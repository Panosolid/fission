## Decisions (defaults, owner may change)

1. **Time is integer ticks, never floating-point seconds.** The timeline counts in flicks: 705,600,000 per second. Every common frame rate and sample rate is a whole number of flicks: one frame at 24 fps is 29,400,000, at 29.97 fps (30000/1001) it is 23,543,520, at 60 fps 11,760,000; one sample at 48 kHz is 14,700 and at 44.1 kHz 16,000. JavaScript numbers hold whole numbers exactly up to 2^53, which is about 147 days of flicks, far beyond the 24-hour limit below. Frame rates are stored as fractions (30000/1001), never as 29.97. Media keeps its own clock (each file's timescale, for example 90,000 or 15,360 per second, which flicks don't always divide) as exact integers, converted to the timeline only at one place with one written rounding rule, and tested there. Why: floating-point seconds drift by a frame over a long timeline, the classic source of off-by-one-frame bugs.
2. **A frame owns a half-open time range.** Frame n of a sequence covers [n × d, (n + 1) × d), where d is the frame duration. A clip from in to out holds frames in ≤ n < out. Every edit, every seek and every export uses this one rule.
3. **Our own file readers and writers, FFmpeg only as the oracle.** The browser decodes and encodes (WebCodecs), but it doesn't read or write the container files, so we write small MP4/MOV and WebM readers and writers ourselves, in TypeScript, checked against FFmpeg's reading of the same files. FFmpeg never ships in the app; it lives in `prototypes/oracle/` and in CI, like OpenCascade and Pillow. Why: each reader is a few hundred lines of exact rules we can test to the frame; a large dependency would hide exactly the timing details we need to get right.
4. **Media is referenced, never copied into the project.** The project's JSON stores each file's name, size, modified time, length, streams and a fingerprint (SHA-256 of the size plus the first and last megabyte). The file itself is found again through a kept file permission where the browser offers one, or a copy in the browser's private storage (the origin private file system) where it doesn't, with a size warning before copying. Proxies, thumbnails and waveforms are caches keyed by the fingerprint: deleting them loses nothing.
5. **The GPU path is WebGL2 first.** It runs in every browser we test, in CI too, and the shared viewport already uses it. WebGPU comes later as a speed-up behind the same interface, only once CI can test it. Every GPU effect has a plain CPU version used only by tests (FT3).
6. **Colour is worked in linear light.** Decoded frames are converted from the file's own colour description (matrix BT.601 or BT.709, limited or full range, transfer) to linear-light floating point; dissolves, opacity, blur and blending happen there; the result is converted back for display and export. Why: dissolving in gamma-encoded values makes a dark dip in the middle of a cross-fade between two bright shots. HDR (PQ and HLG) waits until F14.
7. **One mixer, one renderer, for playback and export.** The audio mixer is pure code run in an AudioWorklet for playback and in a worker for export; the frame renderer is the same for the program monitor and export. What you see and hear is what you export, and export doesn't depend on how fast the computer is.
8. **The audio clock is the master during playback.** Video frames are shown against the audio clock; if the computer is too slow, frames are dropped (and counted), audio never stutters.
9. **Limits, refused with their own message, never a freeze:** sequences up to 24 hours; frame sizes up to 4096 × 4096 (8K later); frame rates 1 to 240 fps; sample rates 8 to 192 kHz; up to 99 video and 99 audio tracks; up to 20,000 clips per sequence. Each limit gets 0.9×/1.1× boundary tests.
10. **Codecs.** Which codecs a browser can decode and encode depends on the browser, the computer and its licences (H.264 and HEVC are patent-licensed and missing from some builds, possibly including the Chromium our CI tests with). We never assume: F1e measures it, and the app asks the browser before every import and export. Tests that need H.264 run in a browser that has it (Google Chrome, which the CI machines carry); a test that can't run there is reported as unsupported, never as passed. Royalty-free VP9 and AV1 in WebM are the fixtures every browser test can use.

### F1. Time and reading files (pure, Node; may run alongside CAD)

- [ ] F1a. Time maths (`src/time.ts`): flicks, frame rates as fractions, frame ↔ time with the half-open rule, media ticks → timeline with the one rounding rule, timecode in and out (HH:MM:SS:FF, and drop-frame HH:MM:SS;FF for 29.97 and 59.94), limits. Test plan: hand-worked: one frame at 30000/1001 is 23,543,520 flicks (705,600,000 × 1001 / 30000); drop-frame 00:01:00;02 is frame 1800 (the first minute holds 60 × 30 = 1800 frames, numbered 0 to 1799, and labels ;00 and ;01 of minute 1 are skipped) and 00:10:00;00 is frame 17,982 (ten minutes of 1800 labels, less 2 skipped in each of the 9 minutes not divisible by ten: 18,000 − 18); a time exactly on a frame boundary belongs to the later frame. Boundaries: 0.9×/1.1× on every limit in decision 9. Seeded random: frame → time → frame is the identity at every supported rate; timecode → frame → timecode too. Breaks: a timecode with a ;-separator at a non-drop rate, minute 1 label ;00 in drop-frame, a fraction with zero denominator, each with its own `VideoError` code.
- [ ] F1b. Test media from the oracle (`prototypes/oracle/video_fixtures.py`): FFmpeg generates small files (a few seconds, small sizes, the whole set under 2 MB) whose frames each show their own frame number as a block pattern with a check bit that survives lossy compression, and whose audio carries 1 kHz beeps starting at known samples; plus FFmpeg's own reading of each (every frame's presentation and decode times, keyframes, durations, the decoded pixels' hash) as JSON beside them in `workspaces/video/test/fixtures/`. Cases: H.264 with B-frames (frames stored out of order), an MP4 edit list that trims the start, AAC with its priming samples, variable frame rate (as phones record), 29.97 fps, odd sizes (1 × 1, 17 × 9), rotation metadata, VP9 and AV1 in WebM, Opus, a file with no audio, a file with no video, a long-GOP file (a keyframe every 10 s). The TS pattern reader (`test/frame-id.ts`). Test plan: the reader finds the right number on every frame of every fixture; a frame with one block flipped is refused (the check bit), not misread; the script is deterministic (same FFmpeg version gives byte-identical files; the version is pinned in the script and checked).
- [ ] F1c. MP4/MOV reader (`src/mp4/`): boxes, the sample tables (time-to-sample, composition offsets, sync samples, sizes, chunk offsets incl. 64-bit, sample-to-chunk), edit lists, each codec's configuration (avcC, hvcC, vpcC, av1C, esds, dOps), the rotation matrix, colour (`colr`), fragmented MP4. Output: every sample's exact presentation and decode time in the file's ticks, its byte range and whether it is a keyframe. Test plan: agrees exactly with the oracle's JSON on every fixture (every frame's times, every keyframe); hand-worked: a tiny MP4 written byte by byte in the test with 3 samples and an edit list starting at sample 2, times worked out in a comment; breaks: each box cut short, a size field pointing past the end, a chunk offset past the end, a sample count that disagrees between tables, a zero timescale, an edit list longer than the media, each its own `VideoError` code; seeded fuzz in `npm test` (FT5): cut and bit-flipped fixtures give a `VideoError` or a valid result, never another exception, never more than a time limit.
- [ ] F1d. WebM/Matroska reader (`src/webm/`): EBML, segment info and timestamp scale, tracks, clusters of unknown size (as browsers record them), SimpleBlocks and BlockGroups, lacing, cues (when present; a file without cues gets its own index built once). Test plan: as F1c: exact agreement with the oracle, a hand-built tiny file with its working in comments, a break for each refusal, seeded fuzz.
- [ ] F1e. Probe, limits and the browser survey: `probe(file)` gives a media description (streams, codecs, size, frame rate or variable, length, colour, rotation, a fingerprint) or a `VideoError` saying what's wrong in plain words ("This file uses ProRes, which browsers can't decode"); and `e2e/video-capabilities.mjs` asks Chromium, Chrome, Firefox and WebKit in CI which decoders and encoders they have (a fixed list of codec strings, sizes and rates) and saves the table as a CI artefact, so the support table in this file comes from measurement. Test plan: hand-worked fingerprint of a fixture (SHA-256 worked out with `sha256sum` on the same bytes, the command in the comment); limits at 0.9×/1.1×; each refusal message tested; the survey's table compared with the previous run's, a change flagged.

## Browser support (to be filled by F1e's survey)
